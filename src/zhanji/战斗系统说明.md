# 战斗系统说明

本文档基于当前代码实现整理，目标是把 `src/zhanji` 里的战斗系统讲清楚，包括：系统结构、回合流程、计算公式、真实结算行为、当前实现中的特殊情况，以及后续优化方向。

本文不是只复述规则文档，而是以当前脚本真实行为为准。设计规则和实际代码不一致的地方，会单独标注。

## 1. 战斗系统整体结构

当前战斗系统是一个“MVU 数据读取 + Vue 界面 + BattleEngine 规则层”的组合结构，核心文件如下：

- `src/zhanji/新建为src文件夹中的文件夹/脚本/战斗系统/index.ts`
  - 负责从 MVU 变量中读取队伍、角色、背包和战斗控制台数据
  - 负责创建战斗 iframe 和 Vue 应用
  - 负责战斗结束后把 HP、MP、金币、经验、背包道具数量回写到 MVU
- `src/zhanji/新建为src文件夹中的文件夹/脚本/战斗系统/store.ts`
  - 负责前端战斗状态机
  - 连接 UI 操作与 `BattleEngine`
  - 控制道具选择、出招、强制换人、捕捉、战斗结果展示等阶段
- `src/zhanji/新建为src文件夹中的文件夹/脚本/战斗系统/engine.ts`
  - 负责所有战斗规则结算
  - 包括伤害、命中、暴击、状态、护盾、回合流程、AI 决策、逃跑、捕捉、奖励
- `src/zhanji/新建为src文件夹中的文件夹/脚本/战斗系统/types.ts`
  - 定义战斗单位、技能、状态、日志、指令、结果、敌方训练家信息等结构
- `src/zhanji/新建为src文件夹中的文件夹/世界书/技能原则.yaml`
  - 是技能 DSL 的设计规则文档
- `src/zhanji/新建为src文件夹中的文件夹/世界书/变量/战斗技能引擎对齐检查清单.md`
  - 是技能生成和引擎对齐用的检查清单

可以把它理解为：

1. MVU 提供角色数据和战斗上下文
2. `index.ts` 把数据转换成战斗可用结构
3. `store.ts` 驱动 UI 与回合状态流转
4. `engine.ts` 负责“这一回合到底发生了什么”
5. 战斗结束后再统一回写数据

## 2. 战斗数据是怎么组织的

### 2.1 战斗单位 `BattleUnit`

每个角色在战斗中会被转成一个 `BattleUnit`，核心字段有：

- 基础属性：`等级`、`元素属性`、`攻击力`、`防御力`、`特攻`、`特防`、`速度`
- 资源：`HP`、`HPMax`、`MP`、`MPMax`、`shield`、`shieldMax`
- 技能：`skills`
- 被动/天赋/光环：`passives`
- 运行时状态：`cooldowns`、`statusEffects`
- 战斗职业：`战斗类型`

这些数据由 `index.ts` 中的 `extractBattleUnit()` 从 MVU 的 `角色数据.*` 中提取出来。

### 2.2 技能结构 `SkillData`

主动技能主要由这些字段组成：

- `类型`
- `稀有度`
- `元素属性`
- `冷却回合`
- `基础威力`
- `描述`
- `效果公式`
- `目标类型`
- `数值参数`

其中真正决定可结算行为的是：

- `效果公式`
- `目标类型`
- `数值参数`

### 2.3 支持的效果公式

当前引擎白名单见 `types.ts`，支持：

- `physical_damage`：物理伤害
- `magic_damage`：魔法伤害
- `heal`：治疗
- `buff`：正向增益
- `debuff`：负向减益
- `drain_physical`：物理吸血
- `drain_magic`：魔法吸血

如果技能没有明确填写合法公式，引擎会在 `engine.ts` 的 `inferFormula()` 里按 `数值参数` 推断：

- 有治疗参数，判定为 `heal`
- 有属性增减参数，按总和正负判定为 `buff` 或 `debuff`
- 有吸血比例，则按 `伤害类型` 推为物理吸血或魔法吸血
- 有基础威力，则按 `伤害类型` 推为物理伤害或魔法伤害

这意味着即使技能定义不够标准，只要字段还在可识别范围内，系统通常不会直接报错，而是走推断兜底。

### 2.4 目标类型

当前引擎支持的目标类型有：

- `single_enemy`
- `self`
- `ally`
- `all_enemies`
- `all_allies`

但要注意，“支持枚举”和“真实结算范围”不完全相同，详细见后文“实际行为与边界情况”。

## 3. 一场战斗是如何开始的

### 3.1 MVU 读取

`index.ts` 会从 `stat_data.战斗控制台` 中读取：

- `进行中`
- `己方出战`
- `敌方出战`
- `己方队伍`
- `敌方队伍`
- `战斗类型`
- `敌方训练家信息`

并通过 `buildTeamNames()` 组装出双方最多 3 人队伍。

### 3.2 角色与道具提取

角色数据来自 `stat_data.角色数据.*`，会被转换成 `BattleUnit`。

背包数据来自 `stat_data.背包`，会被提取为三类战斗道具：

- `属性增强药`
  - 通过名称中是否包含“精华”判断
- `技能增强药`
  - 通过名称中是否包含“技能增强”判断
- `伤药`
  - 通过名称中是否包含“伤药”判断，并进一步识别初级/中级/高级

### 3.3 UI 与引擎初始化

`index.ts` 创建 iframe 后，会在其中挂载 Vue 应用，并在 `store.ts` 里执行：

1. 深拷贝己方和敌方队伍
2. 构造敌方训练家档案
3. 创建 `BattleEngine`
4. 初始阶段进入：
   - 有道具时：`item_select`
   - 无道具时：`selecting`
5. 敌方先执行一次 `planEnemyAction()`，预先生成本回合 AI 指令

## 4. 回合流程说明

当前引擎是 3v3 队伍制，但单回合表现仍然是“前排对前排”的 1v1 结算，后排主要通过换人、全队治疗、场地增益等方式被影响。

### 4.1 战斗前状态

创建 `BattleEngine` 时会：

- 找到双方第一个存活单位作为前排
- 写入开场日志
- 记录敌方训练家类型与 AI 人格

### 4.2 玩家执行一回合

`store.ts` 中的 `executeRound()` 会把玩家输入交给 `engine.executeRound()`，整个回合大致顺序是：

1. 如果己方存在待处理的强制换人，先暂停回合
2. 回合数 `round++`
3. 标准化玩家命令 `normalizePlayerCommand()`
4. 读取敌方已规划的命令，若没有就即时生成
5. 结算回合开始状态提示
6. 处理逃跑/换人指令
7. 按速度决定行动顺序
8. 依次执行双方行动
9. 对满足条件的单位判定是否获得速度追加行动
10. 回合末结算 DoT、护盾、职业特性、场地 buff、强制换人、胜负

### 4.3 回合开始状态处理

`processStatusStartTurn()` 只负责生成提示日志，不直接决定是否真的不能行动。真正阻断行动的逻辑在行动阶段单独判断：

- 冰冻：提示后，在行动阶段直接无法行动
- 麻痹：提示后，在行动阶段按概率无法行动
- 混乱：提示后，在行动阶段按概率自伤并跳过行动

这属于“提示逻辑”和“阻断逻辑”分离的实现方式。

### 4.4 速度决定先手

双方当前出战单位会比较有效速度：

- 高速度先手
- 速度相同则 50% 随机决定先手

有效速度不是纯面板值，而是叠加了状态和场地 buff 之后的结果。

### 4.5 换人处理

换人分为两种：

- 主动换人
- 强制换人

主动换人发生时，本回合该侧不再执行攻击动作。

强制换人通常在角色倒下后触发：

- 己方需要等玩家选人确认
- 敌方会自动从替补里选一个最优对象换上

敌方自动换人逻辑优先考虑：

- 剩余生命比例更高
- 若生命比例相同，则优先速度更高

### 4.6 回合末处理

回合末由 `processEndOfTurn()` 统一处理：

1. 对双方前排结算灼烧/中毒等状态
2. 同步护盾状态
3. 递减状态持续回合
4. 处理状态结束日志
5. 结算职业特性：
   - `重盾型`：回复 `3% HPMax`
   - `均衡型`：回复 `5% MPMax`
6. 递减场地 buff 回合数
7. 若敌方需要强制换人则自动换上替补
8. 检查胜负

## 5. 核心公式汇总

本节按照当前 `engine.ts` 实际公式整理。

### 5.1 属性克制

克制关系：

- 火克风
- 风克地
- 地克水
- 水克火
- 光克暗
- 暗克光

倍率如下：

- 克制：`1.5`
- 被克制：`0.67`
- 同属性互撞：`0.5`
- 无特殊关系：`1.0`

对应实现见 `getTypeEffectiveness()`。

### 5.2 同属性加成 STAB

当技能元素属性和攻击者元素属性一致时，额外乘：

```text
STAB = 1.35
```

### 5.3 暴击公式

基础暴击率：

```text
BASE_CRIT_RATE = 0.0625
```

最终暴击率：

```text
critRate = min(0.5, 0.0625 + 技能暴击率加成 + 被动暴击率加成)
```

暴击伤害倍率：

```text
CRIT_MULTIPLIER = 1.5
```

### 5.4 命中与闪避公式

基础命中率：

```text
base = clamp(skill.命中率 or 0.95, 0.35, 1.0)
```

命中/闪避修正：

```text
acc = clamp(1 + 命中增益总和 - 命中减益总和, 0.6, 1.8)
eva = clamp(1 + 闪避增益总和 - 闪避减益总和, 0.6, 1.8)
```

最终命中率：

```text
hitRate = clamp(base * (acc / eva), 0.3, 1.0)
```

说明：

- 只有伤害类技能会真的进行命中判定
- `heal`、`buff`、`debuff` 这类效果默认不会 miss

### 5.5 属性加减益对基础面板的影响

有效属性由 `getEffectiveStat()` 计算，逻辑是对基础值进行逐个乘法叠加：

```text
攻击 = floor(基础攻击 * (1 + 所有atk_up) * (1 - 所有atk_down))
防御 = floor(基础防御 * (1 + 所有def_up) * (1 - 所有def_down))
特攻 = floor(基础特攻 * (1 + 所有spa_up) * (1 - 所有spa_down))
特防 = floor(基础特防 * (1 + 所有spd_up) * (1 - 所有spd_down))
速度 = floor(基础速度 * (1 + 所有speed_up) * (1 - 所有speed_down))
```

最终最低不会低于 `1`。

### 5.6 伤害公式

当前伤害公式有两套：一套是“带系数”的主公式，一套是“无系数”的兜底公式。

#### 5.6.1 带系数技能

当技能 `数值参数.系数 > 0` 时，使用：

```text
rawDmg = atk * 系数 + 基础威力
defMitigation = def / (def + atk * 0.5)
base = rawDmg * (1 - defMitigation * 0.6) * 0.55
```

其中：

- 物理技能使用 `攻击力` vs `防御力`
- 魔法技能使用 `特攻` vs `特防`

#### 5.6.2 无系数兜底技能

当技能没有 `系数` 时，使用：

```text
ratio = (atk / def) ^ 0.92
base = (((2 * level) / 5 + 2) * max(1, basePower) * ratio) / 60 + 2
```

这个兜底公式的目的是：就算技能定义不完整，也能打出可控伤害，而不是直接失效。

#### 5.6.3 最终伤害主体

在 `base` 基础上继续乘这些修正：

```text
damage = floor(base * 属性倍率 * STAB * 暴击倍率 * 随机浮动 * 全局缩放 * 增伤倍率)
```

其中：

- 属性倍率：克制/被克制/同属性/正常
- STAB：`1.35`
- 暴击倍率：`1.5` 或 `1.0`
- 随机浮动：`0.92 ~ 1.0`
- 全局缩放：`1.15`
- 增伤倍率：来自 `damage_boost` 和 `skill_boost`

### 5.7 单次伤害封顶

当前引擎会根据目标最大生命值对单次伤害做硬封顶，目的是把战斗时长压在一个比较可控的区间。

封顶比例与技能类型、属性克制相关：

#### 带系数技能

- 克制：`38% HPMax`
- 普通：`22% HPMax`
- 被克制：`16% HPMax`
- 同属性互撞：`13% HPMax`

#### 无系数技能

- 克制：`28% HPMax`
- 普通：`18% HPMax`
- 被克制：`14% HPMax`
- 同属性互撞：`12% HPMax`

最终封顶值至少是 `6`。

这一机制会显著压低高爆发技能的上限，是当前平衡设计中的一个核心限制器。

### 5.8 护盾结算

护盾在伤害进入 HP 之前先吸收：

```text
shieldDamage = min(damage, 当前护盾)
护盾 -= shieldDamage
damage -= shieldDamage
HP -= 剩余damage
```

技能授予护盾时：

```text
shieldGranted = 护盾值 + floor(HPMax * 护盾比例)
```

护盾上限：

- 若角色有 `shieldMax`，则以 `shieldMax` 为上限
- 否则以上限 `HPMax`

### 5.9 治疗与吸血

治疗：

```text
healAmt = 治疗量 or floor(HPMax * 治疗比例)
实际回复 = min(healAmt, HPMax - 当前HP)
```

吸血：

```text
drainRatio = clamp(吸血比例 or 0.4, 0.1, 1.0)
healed = min(floor(造成伤害 * drainRatio), HPMax - 当前HP)
```

### 5.10 DoT 与控制状态

灼烧 / 中毒：

```text
dot = max(1, floor(HPMax * value))
```

默认值：

- 灼烧默认伤害比例：`0.05`
- 中毒默认伤害比例：`0.06`

冰冻：

- 行动阶段直接无法行动

麻痹：

```text
skipRate = clamp(value or 0.25, 0.1, 0.8)
```

混乱：

```text
selfHitRate = clamp(value or 0.35, 0.1, 0.9)
selfDamage = max(1, floor(HPMax * 0.06))
```

### 5.11 速度追加行动

如果攻击者速度高于防守者，就有概率立刻追加一次同技能行动：

```text
base = min((攻击者速度 - 防守者速度) / 200, 0.35)
```

- `敏捷型`：追加概率 = `base`
- 其他类型：追加概率 = `base * 0.5`

追加行动只会在目标类型为 `single_enemy` 时触发。

### 5.12 逃跑公式

`tryEscape()` 的公式为：

```text
rate = min(0.95, 0.3 + 0.1 * 逃跑尝试次数 + (己方速度 - 敌方速度) / 220)
```

规则：

- BOSS 战理论上不可逃跑
- 成功则立刻结束战斗，胜者记为 `escape`
- 失败则敌方立刻反击一次，然后推进到回合末结算

### 5.13 捕捉公式

捕捉预览由 `buildCapturePreview()` 计算。

#### 5.13.1 基础率

按品质：

- `E`: `0.9`
- `D`: `0.75`
- `C`: `0.5`
- `B`: `0.25`
- `A`: `0.1`
- `S`: `0.01`

#### 5.13.2 S 级硬锁

如果目标是 `S` 级：

- 最终成功条件只看掷骰是否等于 `1`
- 球倍率、状态修正、辅助器、意志修正、训练师技能加成都失效

#### 5.13.3 球倍率

- `普通球`：`1`
- `高级球`：`1.5`
- `超级球`：`2`
- `魅惑之球`：`1.2`

#### 5.13.4 其他修正

- 捕捉辅助器：`+0.15`
- HP 低于 `5%`：`+0.2`
- HP 不高于 `20%`：`+0.1`
- 目标存在 `麻痹/冰冻/混乱`：`+0.15`
- 意志状态：
  - `坚定`：`-0.3`
  - `动摇`：`-0.1`
  - 其他：`0`
- 训练师技能加成：直接加到最终概率

最终公式：

```text
finalRate = clamp(baseRate * ballMultiplier + techMod + statusMod + resistMod + trainerBonus, 0, 1)
```

掷骰时把 `1~100` 转成 `0.01~1.0` 进行比较。

## 6. 职业特性与被动系统

### 6.1 战斗类型特性

当前代码内置了以下职业特性：

- `强攻型`
  - 造成伤害后，回复 `floor(伤害 * 0.15)` MP
- `重盾型`
  - 每回合末回复 `floor(HPMax * 0.03)` HP
- `魔导型`
  - 使用非 `无` 元素技能造成伤害时，最终伤害乘 `1.2`
- `均衡型`
  - 每回合末回复 `floor(MPMax * 0.05)` MP
- `敏捷型`
  - 吃满速度追加行动概率

这些实现与 `技能原则.yaml` 基本对齐。

### 6.2 被动技能触发

当前被动系统并不是完整的通用被动框架，而是实现了几个明确触发点：

- `on_attack`
  - 目前主要读取被动中的 `暴击率加成`
- `on_hit`
  - 当前框架有触发入口，但默认没有复杂效果展开
- `on_low_hp`
  - 当前血量低于 `30%` 时，如果被动里有正 `防御加成`，会给自己附加一个几乎常驻的防御提升

这说明：

- 被动系统已经有雏形
- 但仍偏“硬编码触发器”，不是可任意扩展的统一事件系统

## 7. 敌方 AI 是怎么运作的

### 7.1 敌方人格来源

`store.ts` 会根据敌方训练家类型，按权重随机出一个 AI 人格：

- `激进`
- `均衡`
- `保守`

人格会影响：

- 低血量时换人阈值
- 低血量时逃跑意图
- 技能评分时的偏好权重

### 7.2 敌方换人倾向

敌方当前前排血量比例低于阈值，且后排还有存活单位时，会考虑主动换人。

阈值由这些因素共同决定：

- AI 人格基础阈值
- 训练家类型带来的逃跑/保守倾向偏置
- 训练家意志状态带来的偏置

最终会从替补中选：

- 血量比例更高者优先
- 血量比例相同则速度高者优先

### 7.3 敌方逃跑倾向

当没有替补可换时，敌方会按当前血量比例、人格、训练家类型偏置、意志状态偏置来决定是否产生“逃跑意图”。

如果触发：

- 本回合敌方指令就是 `escape`
- 回合执行时会直接判定敌方撤退，己方获胜

### 7.4 敌方技能选择

AI 会遍历当前所有可用主动技能，对每个技能打分，主要考虑：

- 基础威力与属性克制
- 命中率
- 异常状态概率总和
- 治疗量/治疗比例
- 是否为己方增益技能
- 对低血量敌人的斩杀价值

大致评分思路是：

```text
总分 = 伤害项 + 状态项 + 治疗项 + 自buff项 + 斩杀项
```

再乘以人格对应的偏好权重。

最终 AI 不是做精确模拟，而是做一层启发式评分，因此可解释性强，但策略深度有限。

## 8. 实际行为与边界情况

这一节非常重要，因为很多行为“看 DSL 似乎支持”，但当前实际实现并不是完全展开的。

### 8.1 当前本质仍是前排对前排结算

虽然系统名义上是 3v3，但绝大多数技能行为仍只影响当前前排：

- 普通攻击只打前排
- 单体技能只打前排
- debuff 也是对前排目标结算
- DoT 也只会在当前前排身上发生

后排更多只是“储备单位”。

### 8.2 `ally` 目标当前等价于 `self`

在 `executeRound()` 中，只要目标类型是 `self` 或 `ally`，实际传入的结算对象都是施法者自己。

也就是说当前没有“给前排之外其他己方单体上 buff/治疗”的实现。

### 8.3 `all_enemies` 当前没有真正打全体

虽然 `目标类型` 白名单里有 `all_enemies`，但在当前回合执行逻辑里并没有遍历敌方全队。

当前实际行为更接近：

- 依旧只对当前前排结算一次

所以如果技能描述写成“打敌方全体”，文档层面必须提醒：当前代码并未真正实现这一点。

### 8.4 `all_allies + buff` 与 `all_allies + heal` 的行为不同

这是当前系统中一个比较关键的特判：

- `all_allies + buff`
  - 不会给全队分别挂状态
  - 会被转成“场地 buff”
  - 场地 buff 只作用当前前排，但会随换人继承
- `all_allies + heal`
  - 会治疗前排和后排全队

这也是规则文档里提到的“前排继承型增益”实际落地方式。

### 8.5 MP 校验与真实扣蓝存在口径差异

这是当前实现里最值得注意的一点。

#### 技能可用性判断

`getAvailableSkills()` 会这样判断技能能否释放：

```text
if (s.消耗MP > unit.MP) 不可用
```

#### 玩家指令校验

`normalizePlayerCommand()` 也会这样判断：

```text
if (unit.MP < desired.消耗MP) 视为 MP 不足
```

#### 真实扣蓝

但 `executeSkill()` 里真正扣 MP 时，不按 `技能.消耗MP`，而是按稀有度固定值：

- `N`: `0`
- `普通`: `5`
- `稀有`: `12`
- `史诗`: `20`
- `传说`: `32`
- `神话`: `45`

这会导致一种实际情况：

- 一个技能显示 `消耗MP = 0`
- 可用性校验通过
- 但出手后仍然会按稀有度扣蓝

也就是说，当前 `消耗MP` 更像是技能数据字段，而不是最终战斗的唯一真实来源。

### 8.6 玩家逃跑路径里存在战斗类型硬编码

`store.ts` 中有 `tryEscape(battleType)`，理论上会把真实战斗类型传给引擎；但在 `engine.executeRound()` 内，如果玩家命令是 `escape`，调用的是：

```text
this.tryEscape('普通')
```

这意味着：

- 从该路径进入时，逃跑逻辑没有使用真实 `battleType`
- `BOSS` 战禁止逃跑的规则在这里可能被绕开

这是当前实现中的明确问题，应该优先修复。

### 8.7 追加行动会再次完整执行技能

当速度追加行动触发时，系统不是“补一次普攻”，而是再次完整执行当前选中的同一个技能，这意味着：

- 会再次扣蓝
- 会再次走技能公式
- 会再次附加状态
- 会再次触发命中/暴击/护盾/击杀判定
- 会再次递减冷却

这会让高速度角色在强技能上获得非常高的收益，也可能让冷却和蓝耗表现得比直觉更快。

### 8.8 冷却回合的处理方式

使用技能时，如果技能冷却大于 0，会先设置：

```text
cooldown = 冷却回合 + 1
```

之后每次行动结束都会统一 `--` 一次。

因此从玩家视角看，冷却是一个“包含当前行动在内”的设计。这个实现没有问题，但文档里必须讲清楚，否则容易误解为多扣了一回合。

### 8.9 护盾日志与真实伤害展示口径

返回的 `ActionResult` 里：

- `damage` 是打进 HP 的部分
- `shieldDamage` 是护盾吸收的部分

但文本日志会写：

```text
造成 damage + shieldDamage 点伤害（护盾吸收shieldDamage）
```

所以从阅读体验上看，是“总打出了多少”，不是“目标实际掉了多少 HP”。

### 8.10 回合开始状态只对当前前排生效

无论是冻结、麻痹、混乱提示，还是回合末的灼烧中毒结算，当前处理的都是“当前前排单位”，不是整队扫描。

这再次说明该系统是“3v3 换人制 + 1v1 前排主结算”的结构。

## 9. 与规则文档的对齐情况

### 9.1 对齐的部分

以下内容与 `技能原则.yaml` 基本一致：

- 技能 DSL 的主字段结构
- 效果公式白名单
- 稀有度自动扣蓝思路
- 战斗职业特性
- `all_allies + buff` 与 `all_allies + heal` 的语义区分
- 缺失公式/缺失系数时尽量兜底而不中断战斗

### 9.2 当前仍存在偏差的部分

- `all_enemies` 在规则层看起来支持全体，但实现中没有真正命中全体
- `ally` 目标在当前实现下等价 `self`
- 逃跑限制在部分路径上没有严格按 `battleType` 执行
- 技能可用性判断与真实扣蓝规则没有完全统一

这些地方都属于“规则文档已给方向，但工程实现还没完全封口”的状态。

## 10. 当前系统的优点与实际表现

### 10.1 优点

- 容错强：技能定义不完整时通常还能打，不容易整场战斗崩掉
- 规则集中：主要战斗逻辑都在 `engine.ts`，排查路径清晰
- 回合节奏可控：单次伤害封顶避免数值爆炸
- 兼容 3v3 展示：虽然主结算是前排对前排，但换人、全队治疗、捕捉、AI 行为已经具备扩展基础
- 设计文档和工程命名基本统一，中文 DSL 可读性高

### 10.2 实际表现特征

- 战斗节奏偏稳定，不容易被一击秒杀
- 高速角色收益很高，特别是能稳定吃到追加行动时
- 高稀有度技能虽然强，但受硬封顶压制，爆发差异不会无限拉开
- 目前更像“前排轮换式回合战”，而不是严格意义上的多目标同步 3v3

## 11. 优化建议

以下建议分成短期修复、中期整理、长期重构三层。

### 11.1 短期修复项

#### 1. 统一 MP 规则

建议把以下几处统一到同一个口径：

- 技能可用性判断
- 玩家指令合法性校验
- UI 显示消耗
- 真实扣蓝

最理想的方式是：

- 明确“战斗内真实 MP 消耗是否永远按稀有度固定值”
- 如果是，就不要再让 `技能.消耗MP` 参与可用性判断
- 改成统一调用一个 `getSkillMpCost(skill)`

这样可以彻底消除“看起来 0 蓝，实际还扣蓝”的问题。

#### 2. 修复逃跑战斗类型硬编码

应修复 `engine.executeRound()` 中玩家逃跑时写死 `this.tryEscape('普通')` 的问题，改为使用真实战斗类型。

这是目前最明确、影响规则正确性的 bug 之一。

#### 3. 明确 `all_enemies` 当前版本语义

如果短期不准备做真正群攻，建议至少做到两件事：

- 文档里明确写“当前只打前排”
- 在技能生成规则里避免描述“同时打后排”

否则策划、AI 生成器和玩家认知会出现偏差。

### 11.2 中期整理项

#### 1. 抽离公式模块

现在 `engine.ts` 已经很大，建议把这些内容拆出去：

- 伤害公式
- 命中与暴击公式
- 状态公式
- 捕捉公式
- AI 评分逻辑

这样好处是：

- 调参更清晰
- 单元测试更容易写
- 平衡设计人员更容易读懂

#### 2. 抽离常量配置表

建议集中管理这些常量：

- 属性倍率
- STAB 倍率
- 暴击率与暴击伤害
- 伤害封顶比例
- 各职业特性倍率
- 捕捉品质基础率
- 球倍率
- AI 人格参数

如果后续要持续调平衡，把这些写在一处会省很多成本。

#### 3. 增加规则对照表

建议补一份“字段 -> 行为 -> 代码入口”的表，例如：

- `治疗比例` -> `heal` -> `executeSkill()`
- `速度加成` -> `buff/debuff` -> `getEffectiveStat()`
- `麻痹概率` -> `buildStatusMessage()` + 行动阶段麻痹判定

这会非常利于后续扩技能、写世界书、做 AI 校验。

### 11.3 长期重构项

#### 1. 把系统真正扩展成完整 3v3

当前系统虽然有 3 人队伍，但大多数结算仍只作用前排。长期如果要做真正的 3v3，可以考虑：

- 让 `all_enemies` 真正遍历敌方全队
- 让 `ally` 可以选择具体友方单位
- 让后排也能持续持有并结算状态
- 引入前后排、站位、保护、嘲讽、连携等机制

这会让系统从“轮换式单挑”升级为真正的队伍战。

#### 2. 被动系统事件化

当前被动触发点是半硬编码的。长期建议改成统一事件总线，例如：

- `before_attack`
- `after_attack`
- `on_hit`
- `on_take_damage`
- `on_turn_start`
- `on_turn_end`
- `on_switch_in`
- `on_defeat`

这样就能把很多职业、天赋、装备、特殊技能效果纳入同一个框架。

#### 3. 让 AI 从启发式评分升级为局面评估

当前 AI 已经可用，但仍然偏“看到什么技能分高就用什么”。长期可以增强为：

- 预估斩杀线
- 考虑 CD 与 MP 未来价值
- 判断对方是否可能追加行动
- 识别状态覆盖收益和浪费
- 区分保命回合与爆发回合

这样敌方行为会更像真正的战斗决策，而不是静态模板。

## 12. 建议的后续实施优先级

如果要继续优化，建议优先级如下：

1. 修复逃跑战斗类型硬编码
2. 统一 MP 消耗规则
3. 明确并收紧 `all_enemies` / `ally` 的当前语义
4. 把公式和常量拆出 `engine.ts`
5. 为伤害、捕捉、追加行动、强制换人补测试
6. 再考虑完整 3v3 和被动事件化重构

## 13. 结论

当前战斗系统已经具备一套可运行、可回写、可扩展的基础框架，核心特点是：

- 使用中文 DSL 驱动技能定义
- 以 `BattleEngine` 为统一规则层
- 采用“3v3 队伍 + 前排主结算 + 换人机制”的结构
- 通过硬封顶、职业特性、AI 启发式评分保证战斗稳定运行

从工程成熟度上看，它已经足以支撑可玩的战斗流程；从系统设计上看，它仍处在“规则已铺好，部分机制尚未完全展开”的阶段。最值得优先处理的问题是规则口径统一，尤其是 MP 与逃跑限制；最值得长期投入的方向是真正的 3v3 化和被动系统事件化。
